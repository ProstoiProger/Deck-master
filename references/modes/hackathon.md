# Mode: hackathon

Judged mainly on the product: impact, innovation, feasibility, user experience and the demo. The deck exists to get
the jury to the demo and to leave them certain the idea can become real.

## Approach

1. **Name the user and the pain**: one person, one problem, one number.
2. **Show the solution in one line**, then go to the demo early (slide 3 to 5).
3. **Demo first, slides second**: build the deck around a screenshot or recording that works offline.
4. **Evidence over adjectives**: one measured result against a baseline, with the source.
5. **Feasibility in one slide**: the architecture in three layers, the key component highlighted.
6. **Path to use**: now, next, later, with what a pilot needs.

## Skeleton

Use `assets/templates/deck-hackathon.md` (8 slides, 3 to 5 minutes): title, problem, solution, architecture, demo,
evidence (`kpi`), roadmap, closing. Allocate time to the rubric weights; see `communication/slides.md`.

## Time

Plan about 45 percent of the event for communication in hackathons judged on the product (`ops/time-budget.md`).
Final hours go to rehearsal and a backup recording, not to features.

## Delivery for judging

- Offline demo or recorded video as the backup; test on the venue machine and resolution.
- Hosted demo only if the data rules allow it.
- PDF copy of the deck on a USB stick or in the submission form; QR code to the repository on the last slide.

## Traps

- Starting with the team or the technology instead of the user's pain.
- A metric slide with no baseline.
- A demo that needs the network and no recording.
- Eight slides of features and no path to use.
- Claiming real users when only the team tried it: say "pilot with N students" only if true.

Bank or corporate events with ML, AI and DS tracks: `modes/hackathon-tracks/README.md`.
